FEATURE 1: Process ID (PID) Namespace Virtualization (CO: 1 & CO: 5)

1. Theory & Operating System Mechanism

The Linux kernel maintains a Process Control Block (PCB, task_struct) for each process. Standard Unix assigns each task a single global integer PID. Without virtualization, any process can see and send signals (e.g., SIGKILL, SIGSTOP) to other host processes. The PID namespace virtualizes the process tree: the container init becomes PID 1 inside its private namespace while maintaining an unprivileged global PID on the host.

2. C System Calls Used

In src/namespaces.c, we allocate a 1MB isolated stack using malloc() and dispatch the clone() system call with CLONE_NEWPID:

sudo ./minicontainer run --hostname isolated-box ./tests/test_info

FEATURE 2: Hostname & Network Identity (UTS) Isolation (CO: 1 & CO: 5)

1. Theory & Operating System Mechanism

The UTS (UNIX Timesharing System) namespace decouples the node hostname (nodename) and domain name from the host. This prevents multi-tenant containers from overwriting each other's identity when calling sethostname().

sudo ./minicontainer run --hostname isolated-box ./tests/test_info
Host Hostname: Tharakesha
--- Running inside container ---
Hostname    : isolated-box
What to say to Evaluators ("Mam"):
"Mam, calling sethostname('isolated-box') modified the hostname strictly within the container's private UTS structure. When the container exits, the host operating system's hostname remains untouched as Tharakesha."

FEATURE 3: Filesystem Sandboxing & Private VFS Mounts (CO: 5)

1. Theory & Operating System Mechanism

Mount namespaces (CLONE_NEWNS) isolate the Virtual File System (VFS) mount table. To prevent container mounts from leaking into the host, we apply MS_PRIVATE propagation. We then invoke chroot() into an isolated Alpine Linux root directory and mount a private /proc pseudo-filesystem.

sudo ./minicontainer run --hostname alpine-node --rootfs ./rootfs /bin/sh

FEATURE 4: Virtual Memory Ceilings, Demand Paging & OOM Killer (CO: 4)

1. Theory & Operating System Mechanism

Linux implements optimistic memory allocation (overcommit) and demand paging. Calling malloc() reserves virtual address space without allocating physical DRAM frames. Only when memory is touched (memset()) does the MMU trigger Page Fault traps. When physical RAM allocation exceeds the cgroups ceiling (memory.max) with swap disabled, the Linux kernel Out-Of-Memory (OOM) Killer terminates the container with SIGKILL (signal 9).

sudo ./minicontainer run --memory 30M ./tests/test_memory 60

FEATURE 5: CPU Bandwidth Quota Throttling (CO: 2)

1. Theory & Operating System Mechanism

Linux CFS Bandwidth Control allocates CPU time using a quota over a 100ms period (cpu.max = quota period). For a 40% cap, quota is 40,000 μs. If an infinite compute loop exhausts 40ms of CPU time in a 100ms window, the scheduler suspends the task from the runqueue.

sudo ./minicontainer run --cpu 40 ./tests/test_cpu 3
[cgroups] CPU quota applied: 40% (40000 us / 100000 us)
[test_cpu] Running intensive CPU calculation for 3 seconds...
[test_cpu] Wall-clock time : 3 seconds
[test_cpu] CPU time used   : 1.12 seconds
[test_cpu] Effective CPU % : 37.4%
What to say to Evaluators ("Mam"):
"Over 3 wall-clock seconds, the CPU loop was restricted to 1.12 seconds of execution time (37.4%), proving deterministic CPU bandwidth throttling via CFS quotas."

FEATURE 6: Proportional Fair-Share CPU Contest (CO: 2)

1. Theory & Operating System Mechanism

In Completely Fair Scheduling, processes receive CPU time proportional to their assigned weights (cpu.weight). When two containers compete on the same CPU core, execution time is partitioned according to their weight ratio.

FEATURE 8: Parent-Child IPC Synchronization Barrier (CO: 3)

1. Theory & Operating System Mechanism

A critical race condition exists if the cloned container child calls execvp() before the parent finishes creating cgroups and attaching the child PID. We implement an IPC barrier using a unidirectional POSIX pipe(): the child blocks on read() until the parent signals completion via write().

FEATURE 9: Process Table Protection & Fork Bomb Defense (CO: 1 & CO: 3)

1. Theory & Operating System Mechanism

A fork bomb rapidly exhausts the kernel's Process Control Block (PCB) table. Cgroups v2 pids.max imposes a hard ceiling on concurrent tasks. Once reached, subsequent fork() calls immediately return EAGAIN (errno 11).

sudo ./minicontainer run --pids 10 ./tests/test_forkbomb 50
[test_forkbomb] Attempting to spawn 50 child processes...
[test_forkbomb] Successfully spawned child process 1 (PID=2)
...
[test_forkbomb] Successfully spawned child process 9 (PID=10)
[test_forkbomb] Fork blocked at process #10! Error: Resource temporarily unavailable (errno=11)
[test_forkbomb] Cgroup pids.max protection successfully prevented resource exhaustion!
[test_forkbomb] Cleaning up 9 spawned processes...
What to say to Evaluators ("Mam"):
"Setting pids.max = 10 prevented process table exhaustion. At the 10th child, fork() was rejected with errno 11 (EAGAIN), keeping the host OS completely safe."
