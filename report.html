1. ABSTRACT

Modern cloud computing and DevOps infrastructure depend fundamentally on container virtualization platforms such as Docker and Kubernetes. However, containers are often perceived as complex abstractions without an understanding of the underlying kernel architecture.

This project designs, implements, and evaluates mini-container, a standalone, lightweight container runtime written from scratch in pure C99 with zero third-party libraries. By directly interfacing with Linux kernel subsystems—specifically Linux Namespaces (CLONE_NEWPID, CLONE_NEWUTS, CLONE_NEWNS, CLONE_NEWIPC), Unified Cgroups v2 (memory.max, cpu.max, cpu.weight, pids.max), and VFS filesystem sandboxing—the runtime achieves complete hardware resource confinement and process tree isolation.

The project experimentally demonstrates all five Course Outcomes (CO: 1 to CO: 5) of the Operating Systems syllabus, including system call dispatch, Completely Fair Scheduling (CFS), POSIX semaphore synchronization, demand paging accounting (minor and major page faults), and kernel Out-Of-Memory (OOM) Killer execution.

6. VIVA VOCE DEFENSE CHEAT SHEET (TOP FACULTY QUESTIONS)

Q1: Why did you use clone() instead of standard fork()?

Answer: fork() duplicates the process in the exact same namespaces. clone() accepts flags like CLONE_NEWPID and CLONE_NEWUTS, instructing the Linux kernel to instantiate the child directly inside brand-new, isolated namespaces.

Q2: Why did your memory test trigger SIGKILL instead of malloc() returning NULL?

Answer: Linux uses optimistic memory allocation (overcommit) and demand paging. malloc() initially reserves virtual address space without committing physical pages. When memset() touched the pages, memory demand crossed memory.max. With swap disabled, the kernel Out-Of-Memory (OOM) Killer stepped in and dispatched an uncatchable SIGKILL.

Q3: What is the purpose of the POSIX pipe between parent and child?

Answer: It acts as a barrier synchronization mechanism (CO: 3). Without it, a race condition occurs where the child might call execvp() before the parent finishes creating the cgroup and writing the child's PID into cgroup.procs.

Q4: How did your project prove CPU scheduling fairness?

Answer: We ran two containers simultaneously pinned to CPU Core 0 with CFS weights of 800 and 200. The high-weight container received 2.78 seconds of CPU time while the low-weight container received 0.69 seconds, achieving an exact 4:1 execution ratio matching theoretical scheduling weights.

Q5: What are Minor Page Faults and how did you verify them?

Answer: Minor page faults occur when virtual pages are mapped to physical RAM without requiring disk I/O. We parsed /sys/fs/cgroup/minicontainer-[PID]/memory.stat and recorded over 7,700 minor page faults during memory allocation, proving demand paging in the memory management unit.

The mini-container project demonstrates that robust operating system virtualization, process isolation, CPU scheduling, concurrency synchronization, and memory protection can be achieved purely using native Linux kernel subsystems in C with zero external runtime overhead.
