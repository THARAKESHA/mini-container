Concept: Containers vs Virtual Machines
Motivation

Traditional Virtual Machines (VMs)

  • Virtualize the hardware layer using hypervisors.
  • Requires a full duplicate guest OS kernel per instance.
  • High RAM footprint (GBs) and slow multi-second boot times.
  • Incurs hardware emulation translation penalties.

OS-Level Containers (Our Implementation)

  • Shares the single underlying Linux kernel.
  • Containers are regular OS processes wrapped in kernel-enforced isolation boundaries.
  • Sub-second boot times (10-20ms) and minimal RAM footprint.
  • Near-native bare-metal execution performance.

System Architecture & Process Flow
Process Lifecycle

Execution Flow Lifecycle

1. CLI Invocation:
   └─► sudo minicontainer run --memory 30M --cpu 40 /bin/sh

2. Host Parent Process:
   ├─► Allocates 1MB stack for child
   ├─► Opens UNIX synchronization pipe (barrier)
   ├─► clone(CLONE_NEWPID | CLONE_NEWUTS | CLONE_NEWNS | ...)
   ├─► Creates /sys/fs/cgroup/minicontainer-[PID]
   ├─► Applies memory.max, cpu.max, pids.max
   ├─► Attaches child PID to cgroup.procs
   ├─► Unblocks child via sync pipe
   └─► Calls waitpid(), reads memory.stat, cleans cgroup

3. Container Child Process:
   ├─► Blocks on pipe until cgroups are attached
   ├─► sethostname("container-box")
   ├─► chroot() to rootfs & mounts private /proc
   └─► execvp(argv[0]) as PID 1

Key Engineering Highlights

  • Race-Free Attachment: Child pauses on an IPC pipe until parent establishes cgroup limits, eliminating race conditions.
  • VFS Isolation: Marks root mount as MS_PRIVATE to prevent container mounts from leaking into the host OS.
  • Real-Time Kernel Accounting: Reads memory.stat upon exit to record peak RAM, minor page faults, and major page faults.
Core Isolation Primitives in Linux
Kernel Features

1. Namespaces

What the process can SEE

  • CLONE_NEWPID: Child becomes PID 1; host processes hidden.
  • CLONE_NEWUTS: Isolated hostname.
  • CLONE_NEWNS: Isolated VFS mount table.
  • CLONE_NEWIPC: Separate IPC semaphores & queues.

2. Cgroups v2

What the process can USE

  • memory.max: Strict physical RAM ceiling; triggers OOM killer.
  • cpu.max: CFS scheduler bandwidth quota.
  • cpu.weight: Proportional fair share scheduling.
  • pids.max: Prevents fork bomb attacks.

3. Rootfs Sandboxing

Where the process can TOUCH

  • Uses Alpine Linux userland (~3.5MB).
  • chroot() prevents traversal into host directories.
  • Private /proc mount enables isolated ps output.

Technical Review & Viva Defense
Faculty Q&A

Q1: Why clone() instead of fork()?

fork() duplicates the process in the exact same namespaces. clone() accepts flags like CLONE_NEWPID and CLONE_NEWUTS, creating the child directly inside brand-new, isolated kernel namespaces.


Q2: Why did memory limit trigger SIGKILL?

Linux uses optimistic memory allocation (overcommit) and demand paging. When memset() committed physical pages exceeding memory.max with swap disabled, the OS kernel OOM Killer dispatched an uncatchable SIGKILL.

Q3: Why is an IPC pipe needed?

To prevent a race condition. The child must not call execvp() before the parent finishes creating the cgroup and writing the child's PID into cgroup.procs.


Q4: How was CPU fair share verified?

Two containers with weights 800 and 200 ran concurrently on CPU 0. CFS allocated 2.78s and 0.69s of CPU time, verifying the theoretical 4:1 scheduling ratio with 99.5% accuracy.
